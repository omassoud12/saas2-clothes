# Owner Dashboard: running report

Branch `owner-dashboard`. Production is never touched: migrations, seeds and tests run on the local
embedded Postgres (`backend/scripts/dev-db.mjs`).

## Phase 1 — Audit

- Gap report: `docs/dashboard-gap-report.md`.
- Decisions:
  - **No Membership table**: `User` is already the account membership (one auth user = one account).
  - **Roles**: `UserRole` stays SUPER_ADMIN / OWNER / WAREHOUSE (DB triggers depend on it). Employees
    get `employeeRole` = MANAGER / CASHIER / WAREHOUSE as the preset; existing employees are WAREHOUSE
    and keep exactly the access they have today.
  - **Names**: `ProductVariant.lastPurchaseCost` is the current unit cost, `SaleItem.unitCostAtSale` the
    snapshot. Money stays `Decimal(18,2)` like the rest of the schema (the spec says 12,2; wider is safe).
  - **Mail**: Supabase Auth sends every mail (invite, reset). No SMTP / Resend is added.

## Phase 2 — Database

Migrations (applied to the local database only):
- `20261103100000_expense_category_internet`: `ExpenseCategory` + `INTERNET` (alone: a new enum value
  cannot be used in the transaction that adds it).
- `20261103100100_owner_dashboard` (one transaction, additive):
  - `User`: `employeeRole` (MANAGER / CASHIER / WAREHOUSE), `status` (INVITED / ACTIVE / DEACTIVATED),
    `mustChangePassword`, `deactivatedAt`, `deactivatedById`, `permissions text[]`, `permissionsCustom`.
    Existing WAREHOUSE users get `employeeRole = WAREHOUSE`; inactive users become DEACTIVATED.
    CHECKs: `employeeRole` is set exactly for WAREHOUSE users; `isActive = (status = ACTIVE)`.
  - `UserStore`, `Invite` (token SHA-256 only, lowercase email), `AuditLog`, `CostEntry`,
    `RecurringExpense`, `ProductVariant.costUpdatedAt`.
  - `Expense`: `storeId`, `recurringExpenseId` (unique per month), `originalAmount/Currency`, `note`,
    `deletedAt`. The append-only trigger now allows editing the owner-editable fields, still refuses any
    DELETE, freezes a removed expense and never lets identity, author, currency or month link change.
  - RLS on and no privileges for `anon` / `authenticated` on the new tables, like every table.
  - The diff generated by Prisma wanted to drop the two hand-written `NULLS NOT DISTINCT` unique indexes
    of the business migration; those lines were removed (they are not in the Prisma schema on purpose).
- Removed expenses (`deletedAt`) are left out of the expense list, the Business Monthly / Yearly and
  the daily financial report.
- Business Monthly lists the new Internet category.

Decisions:
- `Decimal(18,2)` for money (like the rest of the schema).
- No SaleItem cost backfill: `unitCostAtSale` already exists and is set in the sale transaction; sale
  lines are immutable by trigger, so old lines without a cost stay "unknown" (shown as missing cost).
- `SalesTarget` already has the unique (account, store, period, periodStart) index; no change.
- Sales have no `storeId`; the existing `Sale(accountId, status, createdAt)` and
  `SaleItem(accountId, variantId, createdAt)` indexes serve the dashboard queries.

Results: typecheck OK; backend tests 13,724 / 13,724.

## Phase 3 — Dashboard summary and best sellers

- `src/access/permissions.ts`: pages (DASHBOARD, POS, SALES_HISTORY, PRODUCTS, INVENTORY,
  BUSINESS_REPORTS, EMPLOYEES, EXPENSES, TARGETS, SETTINGS), capabilities (VIEW_COST_PROFIT,
  EDIT_PRODUCT_COST, GIVE_DISCOUNT, VOID_SALE), role presets, `requirePermission` /
  `requireAnyPermission`. The auth middleware now refuses INVITED (403 `MEMBER_INVITED`) and DEACTIVATED
  members and puts the member's effective permissions on `req.auth`.
- Business reports use the capability: a member with VIEW_COST_PROFIT sees cost/profit (and Yearly); the
  report cache key follows the capability instead of the role.
- `GET /api/dashboard/summary?storeId` and `GET /api/dashboard/best-sellers?period&sort&limit&storeId`
  (`src/dashboard/`), DASHBOARD permission, built only on `business/day-totals.ts`:
  - today live; yesterday cut at the current shop time; the month from rollups + today live;
  - target: `progress` = month sales / target (4 decimals), `expectedByToday` = target × day / days;
  - `projection` = finished days as sold + max(today, today's usual day) + the usual sales of the days to
    come (the same 4-same-weekday forecast as Business);
  - `month.expensesTotal` / `netProfit` use the same spread expenses as Business Monthly, so the numbers
    match; `expensesThisMonth` lists what was entered for the month (not spread);
  - `missingCost`: active variants without a cost and what was sold without a cost in the last 30 days
    (driven by `Sale(accountId, status, createdAt)`);
  - `employees` only with EMPLOYEES; cost, profit and expenses null without VIEW_COST_PROFIT;
  - best sellers grouped by product with variants, the same `productRows` as Business; `sort=profit`
    is 403 without VIEW_COST_PROFIT.
  - Cache 30 s in the shared report cache, key account:store:kind:params:what-the-member-may-see, ETag
    / 304, in-flight coalescing, 120 requests / minute / account.

Decision: the top-level month key is `currentMonth` (the spec's `month` object holds the numbers).

Results: dashboard tests 7 / 7 (numbers equal Business Daily / Weekly / Monthly, permissions, tenant
isolation); backend 13,731 / 13,731; typecheck and build OK.
